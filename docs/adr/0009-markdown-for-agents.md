# ADR-0009: markdown content negotiation for agents

> Amended on 2026-10-30 by [#190](https://github.com/ntatoud/noe.tatoud.com/issues/190): every page now has a markdown twin. A static page that is neither home nor a listing, such as `/styleguide`, gets a generic twin (its title, description and a link to `/llms.txt`) and is listed under "Other pages" in `/llms.txt`. The "pages with no content behind them stay HTML-only" consequence below no longer applies to any current page.

A request carrying `Accept: text/markdown` gets a markdown representation of the page; everything else still gets HTML. The markdown is generated at build time by `@ntatoud/content/vite-markdown` as a `.md` file next to each page, and a Netlify edge function, `netlify/edge-functions/markdown-negotiation.ts`, maps the route onto it. `/llms.txt` is generated by the same step.

## Why

Agents read this site, and HTML is a bad format to read it in: the markup, nav, footer and inlined highlighting classes are most of the bytes and none of the meaning. [Markdown for Agents](https://developers.cloudflare.com/fundamentals/reference/markdown-for-agents/) established `Accept: text/markdown` as the way to ask for better, and it costs nothing to answer — the content is authored in markdown, so the good representation is the one we started from.

`netlify.toml` had also been advertising `Link: </llms.txt>; rel="describedby"` since ADR-0005 while nothing served that file. It is generated here.

## Why the edge, and not the app

Cloudflare offers this as a zone setting with no application code. This site is on Netlify, so it has to be built — and it cannot be built in the app.

Pages are prerendered and published as static files (ADR-0008). Netlify's [request chain](https://docs.netlify.com/resources/troubleshooting/request-chain/) puts edge functions at step 5 and static file serving at step 12, with serverless functions at step 10. A request for `/blog/what-is-mcp` is answered off the CDN from `dist/client/blog/what-is-mcp/index.html` and never reaches application code, so no route handler, server function or middleware can see the `Accept` header. The edge is the first place in the chain that can.

## Why build-time markdown, and not conversion at the edge

The edge function could fetch the HTML and convert it. It doesn't, because:

- `@ntatoud/effect-collections` already carries each document's `source` — the authored markdown. Converting HTML back to markdown would be a lossy round trip to arrive somewhere worse.
- A converter would also have to strip the header, nav and footer that wrap every page, i.e. re-derive which part of the document is the content.
- Conversion per request is latency and CPU at the edge on every agent hit, for a result that can only change on deploy.

So the build emits the markdown and the edge function only routes. It fetches a static file and re-labels the response; nothing is converted per request.

## Shape

One derivable rule maps a route to its markdown, so the edge function needs no manifest and exactly one fetch:

| Route          | Markdown          |
| -------------- | ----------------- |
| `/`            | `/index.md`       |
| `/blog`        | `/blog.md`        |
| `/blog/<slug>` | `/blog/<slug>.md` |

The `.md` files are real, fetchable URLs, not just an internal target — `llms.txt` and the listing markdown link to them directly, so an agent that starts at `/llms.txt` can follow markdown all the way down without re-negotiating on every hop.

A document's markdown is a header built from its frontmatter (title, description, the metadata the page shows in its chrome, a canonical link) followed by its authored body with the frontmatter block stripped. Body image references are rewritten to the absolute URL of the hashed asset that actually serves them, resolved out of the Rollup bundle by `originalFileNames` — leaving them relative would hand an agent 404s, since nothing serves `content/` at runtime.

Drafts get a markdown twin, matching the detail pages `content()` generates: an unpublished document keeps a reachable page, so it keeps a reachable representation. Listings and `llms.txt` include only published documents.

## Consequences

- **The `Accept` decision is duplicated.** `prefersMarkdown` and `markdownPath` exist twice. Netlify runs edge functions on **Deno**, which makes this file the only thing in an otherwise all-Node repo that does not share the workspace's runtime — and `@ntatoud/content` is a private pnpm workspace package, symlinked outside the deploy root, whose graph pulls in `effect` and `NodeFileSystem`. Importing a zero-dependency leaf module by relative path would likely bundle fine, but that is only verifiable by deploying, so the duplication was the safer trade. `packages/content/test/markdown.test.ts` imports the edge function and asserts the two agree across every `Accept` header and route in a table — without it the drift would be silent, with dev serving markdown while production quietly stopped. If the shared-leaf-module route is ever proven at deploy, that test becomes the safety net for removing the copy.
- **`Accept` is parsed, not substring-matched.** `text/markdown;q=0.5, text/html` has asked for HTML and gets it. `*/*` is deliberately not counted as a vote for HTML, so `text/markdown, */*` gets markdown.
- **`x-markdown-tokens` is an estimate** — four characters per token — and is labelled as one. It exists so an agent can size a fetch against its context window before committing; a real tokenizer would mean shipping one model's vocabulary to the edge for precision nothing here needs. `x-original-tokens` is not sent, since it would require fetching the HTML too.
- **Browser traffic pays nothing.** `config.header` is a regex pre-filter Netlify evaluates _before_ invoking the function, so a request whose `Accept` never mentions markdown skips it entirely — no invocation, no added latency on a normal page load. It is only a necessary condition: it cannot weigh q-values, so `prefersMarkdown` still makes the real decision. The invariant that matters runs one way — the regex may over-match, but must never reject something `prefersMarkdown` would accept, or markdown silently dies for those clients — and the test asserts exactly that.
- **`Vary: Accept` is set on markdown responses only, not on page HTML.** The textbook answer is to set it on both, but Netlify folds standard `Vary` into its cache key and browsers each send a different `Accept` string, which would split one cached page into several entries per edge location and lower the hit rate on every browser page load. (Netlify's own `Netlify-Vary` refuses high-cardinality request headers for the same reason.) It is also not needed to keep the representations apart: the edge function runs before the edge cache and returns markdown directly, so markdown is never stored under the page URL, and HTML entries are only created by requests that skipped the function. The residual gap is an agent-side cache that fetched HTML first and later asks for markdown; `netlify.toml` records how to close it if that ever shows up.
- **Nothing is added to the JS bundle.** The plugin only calls `emitFile`; it never joins the module graph. Verified by building with and without it — all 97 hashed JS/CSS assets come out byte-identical, and the output grows by 80 KB of static text.
- **Pages with no content behind them stay HTML-only.** `/styleguide` has no markdown twin; the edge function bows out and the prerendered HTML is served. The dev middleware rewrites `Accept` to `text/html` in that case, because TanStack's SSR handler would otherwise answer a non-HTML `Accept` with the route's JSON payload — a divergence that only shows up in dev.
- **The dev server negotiates too**, through the same plugin, so the route-to-markdown mapping is exercised by `pnpm dev` instead of first being tested on deploy.
- **Page copy has one home.** The listing descriptions moved to `apps/web/src/lib/site.ts`, read by both the routes' `<meta>` tags and the generated markdown, so the two cannot describe a page differently.
