## The short version

A large mutual insurance group wanted one React library for every component that has nothing to do with the business: form fields, autocompletes, toasts. Without one, every internal team was rebuilding its own.

I joined in February 2025, five months after the library started, and ended up responsible for it. For 17 months I was the person between the design system team upstream and the teams using the library downstream.

- **50+ developers** building on it
- **80+ components**
- **7 to 8 teams**, on about ten projects
- Around **eight months full-time**, then part-time until June 2026

The code is private, so there's no demo or repo to link. I told the same story in a talk: [Evolving an Internal React Library](/talks/evolving-an-internal-react-library).

## My role

- **Building** the components, and changing them as requests came in from both sides: the business needs of the teams, and changes to the design system.
- **Owning releases**: versioning, deprecations, changelog, migrations.
- **Supporting the teams**: documentation, and answering their questions.
- **Being the main point of contact** with the design system team and with the teams using the library.

Two to three developers worked on the library at any one time, and five others rotated through it alongside me over the 17 months. With the team always changing, three things held it together: the Storybook docs, strict conventions, and me as the go-to person.

What I didn't own: the HTML and CSS, which came from the design system team, and the teams' upgrade schedules. They decided when to move to a new version.

## The constraint: the markup was given

The design system wasn't a Figma file or a set of tokens. It shipped as **HTML and CSS**, so the DOM was decided before we wrote a line of React. Our job was to put a layer on top: hide the design system's complexity and add the JavaScript it didn't have.

This is what a team had to write for one email field without the library:

```html
<div class="form-group form_field--wrapper input-container mt-2">
  <label for="email-field" class="field-label fieldLabel required-label">
    Email <span aria-hidden="true">*</span>
  </label>
  <input
    id="email-field"
    class="form-control input--text field__input inputField"
    type="email"
    aria-required="true"
    aria-describedby="email-error"
    aria-invalid="true"
  />
  <span
    id="email-error"
    class="error-msg field-error errorMessage"
    role="alert"
  >
    Invalid email
  </span>
</div>
```

And this is what they write with it, with the ids, ARIA attributes and error wiring handled for them:

```tsx
<TextField
  name="email"
  label="Email"
  type="email"
  isRequired
  error="Invalid email"
/>
```

That fixed DOM shaped every decision that follows.

## Keeping React Hook Form optional

The library has three layers:

1. **Presentational components**, wrapping the design system.
2. **Form fields**, the inputs themselves.
3. **A form layer on top**, adding React Hook Form integration and the accessibility wiring.

Putting React Hook Form in its own layer was deliberate. An internal library inherits every app the company already runs, and some of those apps are old. If the fields required React Hook Form, only new projects could adopt them. As a separate layer, older apps could use the plain fields and newer ones could opt in.

## From one big component to composition

The first version of `Field` took everything as props. That works for the default case. Then someone needs helper text in a different place, or a "Forgot password?" link next to the label, and the component grows another prop. It becomes a snowball: it can't cover every need, yet it ships everything to teams that need one or two of those things.

```tsx title="v3"
<Field
  label="Email"
  type="email"
  required
  helpText="you@example.com"
  error={errors.email}
/>
```

For v4 I split it into primitives that share state through context. `Field.Root` passes `required` and `invalid` down, `Field.Label` links itself to the input's id, and `Field.Error` only renders when there's an error:

```tsx title="v4"
<Field.Root required invalid={!!errors.email}>
  <Field.Label>Email</Field.Label>
  <Field.Input type="email" />
  <Field.HelpText>you@example.com</Field.HelpText>
  <Field.Error>{errors.email}</Field.Error>
</Field.Root>
```

The default case stays a one-liner, because the ready-made `TextField` is just these primitives assembled. The unusual case is built from the same pieces instead of from new props.

**Composition, but not headless.** Headless libraries let you place each part wherever you like and bring your own markup. We couldn't: the design system decides the markup. So the primitives compose in the arrangements the design system allows, and they always render its DOM.

Since there was no HTML to follow, I built the DOM myself, based on the existing components. Teams already knew those patterns, and I didn't want the new component to break them.

## Types as documentation

A loose type lets mistakes through without a sound. With `status?: string`, a typo like `"succes"` compiles and fails silently. The fix is a stricter type. Wherever a prop's meaning depends on another prop, a discriminated union says so:

```ts
type ToastStatusProps =
  | { status: 'info'; message: string }
  | { status: 'success'; message: string }
  | { status: 'error'; message: string; retry?: () => void }
```

Now `retry` on a success toast is a compile error, and autocomplete in the editor tells you what each status accepts. For teams that never open the docs, the types _are_ the docs.

## Docs and tests that match real use

There was a Storybook, but it only showed the default case of each component. A component you can assemble ten ways needs more than one example, and when teams can't see how to do something, they work around it: they copy-paste, or build their own.

- **One story per use case**, not one per component. Storybook became live documentation developers could try directly, and the place where they reported bugs.
- **An accessibility check on every story.**
- **Tests in a real browser.** Our old tests mostly checked that a component rendered, which says nothing about focus, keyboard navigation or floating elements, the things a component library gets wrong. Vitest browser mode runs them in a real browser.
- **Every bug fix comes with a regression test.**

AI sped up that last part without cutting corners: describe the expected behaviour, generate the tests, generate the code, check that the whole suite passes, then review it by hand.

## Shipping to teams I didn't manage

Releases worked one way: we published to a private npm registry, and each team upgraded whenever it chose. I couldn't force anyone to upgrade, so every breaking change cost 7 or 8 teams time they hadn't planned for. The release policy followed from that:

- **As few major versions as possible.** Breaking changes were grouped rather than shipped whenever an API turned out wrong.
- **Deprecations kept few and collected until the next major**, so a bad API could survive, flagged, instead of disappearing overnight.
- **A changelog that writes itself.** On my first day I couldn't tell what had changed between versions. I set up git-cliff to generate the changelog from commits, so every release says what changed.
- **Knip to find dead code**, because you can't deprecate what you don't know is unused.
- **oxlint and oxfmt with Lefthook**, replacing ESLint and Prettier. They're much faster, and linting and formatting come from one toolchain.

The obvious fix was a codemod: a script that rewrites their code from the v3 API to v4. We had always ruled codemods out because they took too long to write for what they saved. With AI, writing one became cheap, and the migration itself runs in about thirty seconds.

I left before I could see whether that team fully caught up. What I take from it is that when a tool gets cheaper, an option you had ruled out can become the right call.

## When the upstream broke us

The design system team didn't version its markup changes. When they changed the HTML, we found out because the library broke. No release notes, no warning.

That was the hardest part of the job, and the most useful lesson. We protected our users with rare majors and announced deprecations, while our own upstream gave us no such warning. We were on the receiving end of exactly what we refused to do to the teams using the library.

## Where it is now

The library is still in use. It's much more stable than when I joined, and the work around it is now mostly support rather than new components. I'm proud of what we built.

I left in June 2026, not because anything went wrong, but because another client needed me full-time. One honest note on adoption: using the library was a company decision, so the number of teams measures that decision as much as the library itself.

## What I learned

Almost none of it is technical, even though this was my longest project.

- **Documentation people can use.** Writing the docs is one skill. Writing docs that teams of very different levels actually understand is the harder one.
- **Supporting teams is half the job.** A library isn't just an API: you ship a tool, and people still have to learn how to use it well.
- **Saying no.** Accepting every request on a shared library means doing the work other teams don't want to do. Sometimes the right answer is to hand the question back.
- **Working inside a large organisation.** It was my first time dealing with heavy processes, and learning to keep my frustration in check was part of the job.
- **A bit of team management**, with developers rotating on and off the library.

Some of it came with me to my next project: oxlint and oxfmt, and the habit of handing AI large, mechanical changes that a type checker can verify.
